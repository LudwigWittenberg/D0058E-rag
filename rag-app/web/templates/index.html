The RAG Pipeline in One Picture

Document → Chunk → Embed → Store → Retrieve → Generate

1. Upload a document (PDF, TXT, MD)
2. Chunk it into smaller passages (configurable size)
3. Embed each chunk into a vector (using sentence-transformers)
4. Store vectors in ChromaDB
5. Retrieve the most relevant chunks for a user query
6. Generate an answer grounded in the retrieved context

Why RAG?

  • No hallucination — answers are grounded in your documents, not made up
  • Private knowledge — works with internal/proprietary documents the model was never trained on
  • Up-to-date — add new documents anytime without retraining the model
  • Source attribution — shows which chunks the answer came from
  • Scalable memory — retrieves from thousands of documents in milliseconds

1. Goal

Build and tune a Retrieval-Augmented Generation (RAG) pipeline that grounds LLM responses in uploaded documents. You will experiment with every stage of the pipeline — chunking, embedding, retrieval, and generation — to understand how each parameter affects answer quality. By the end, you will have a working Q&A system that answers questions accurately from your own documents.

Why RAG?

In Lab 1 you built a chatbot — but you may have noticed that LLMs have a fundamental limitation: all their knowledge comes from the training phase. The model compresses its training data into internal parameters (its parametric knowledge), and by default it has no access to external or up-to-date information.

This becomes obvious when you ask about something the model was never trained on. For example, try asking your chatbot:

"What are the key changes in Sweden's 2026 Spring Budget (Vårändringsbudgeten 2026)?"

The model will either hallucinate an answer, refuse, or give outdated information — because this document was published after its training cutoff. The same problem applies to any private or recent material: your university's course syllabus, a company's internal documentation, or a research paper published last week.

RAG solves this by retrieving relevant content from your own documents at query time and injecting it into the prompt. The LLM then generates an answer grounded in that retrieved context — combining its language ability with your source material. The model doesn't need to "know" the answer; it just needs to read the relevant text you provide.

📝 Why not LangChain?

You may have seen tutorials that use LangChain to build RAG pipelines in just a few lines of code. LangChain is a popular framework that wraps LLM calls, embeddings, vector stores, and retrieval chains behind high-level abstractions.

In this course, we intentionally do not use LangChain. Instead, every step is implemented explicitly:

  • Chunking → ai/chunker.py (plain Python sliding window)
  • Embeddings → ai/embeddings.py (direct sentence-transformers calls)
  • Vector store → ai/vectorstore.py (direct ChromaDB client)
  • LLM calls → shared/llm_client.py (direct Ollama HTTP API)
  • Prompt construction → ai/generator.py (string formatting)
Why? So you see exactly what happens at each stage. When LangChain does RetrievalQA.from_chain_type(...), it hides the embed → search → format → generate flow. By writing it yourself, you understand the trade-offs and can debug each piece independently. Once you understand the fundamentals, adopting LangChain (or LlamaIndex, or any other framework) later becomes straightforward.

5. Concepts You Need to Understand

The RAG Pipeline

Document → Chunk → Embed → Store → [Query] → Retrieve → Augment Prompt → Generate Answer

Why RAG?

LLMs have two types of knowledge:

  • Parametric knowledge — baked into weights during training (static, may be outdated)
  • Source knowledge — provided in the prompt at query time (dynamic, always current)

RAG provides source knowledge by retrieving relevant document chunks and injecting them into the prompt.

Key Parameters

ParameterWhat it controlsTrade-off
chunk_sizeCharacters per chunkSmall = precise but fragmented; Large = contextual but noisy
chunk_overlapShared characters between consecutive chunksMore overlap = less information loss at boundaries
top_kNumber of chunks retrievedMore = broader context; fewer = more focused
embedding_modelWhich model converts text to vectorsLarger = better quality but slower
temperatureLLM creativity in generationLower = more faithful to context; higher = more creative

Cosine Distance vs. Cosine Similarity
The cosine formula cos(θ) = (A·B) / (||A|| × ||B||) computes similarity — a value from −1 to +1 indicating how much two vectors point in the same direction.

ChromaDB converts this to a distance for sorting (databases need "closest first"):
cosine_distance = 1 − cosine_similarity
  • Distance = 0 → vectors point in the same direction (similarity = 1, identical meaning)
  • Distance = 1 → vectors are orthogonal (similarity = 0, unrelated)
  • Distance = 2 → vectors point in opposite directions (similarity = −1)
ChromaDB sorts results by ascending distance (closest first), which is equivalent to sorting by descending similarity.

Task 2.7 — BONUS: Implement MMR Retrieval

Difficulty: ★★★   File: ai/retriever.py

Background

Standard similarity search returns the top-K most similar chunks. But these chunks might all say the same thing (e.g., if a concept is mentioned in multiple paragraphs). Maximal Marginal Relevance (MMR) balances relevance with diversity — it selects chunks that are relevant to the query but also different from each other.

The MMR formula:

MMR(chunk) = λ × similarity(chunk, query) - (1-λ) × max(similarity(chunk, selected_chunk))

Where:

  • λ = 1.0 → pure relevance (same as standard search)
  • λ = 0.5 → balanced relevance and diversity
  • λ = 0.0 → pure diversity (maximally different chunks)

        top_k: Number of final results to return.
        fetch_k: Number of candidates to fetch before MMR filtering.
        lambda_mult: Balance factor (1.0 = pure relevance, 0.0 = pure diversity).
        collection_name: ChromaDB collection to search.
        persist_directory: Path to ChromaDB storage.

    Returns:
        List of RetrievalResult objects selected by MMR.
    """
    import numpy as np
    from ai.embeddings import embed_text
    from ai.vectorstore import VectorStore

    if persist_directory is None:
        app_root = Path(__file__).resolve().parent.parent
        persist_directory = str(app_root / "data" / "chromadb")

    # Step 1: Embed the query
    query_embedding = embed_text(query)

    # Step 2: Fetch more candidates than needed
    store = VectorStore(persist_directory=persist_directory)
    results = store.query(
        query_embedding=query_embedding.tolist(),
        top_k=fetch_k,
        collection_name=collection_name,
    )

    documents = results.get("documents", [])
    distances = results.get("distances", [])
    metadatas = results.get("metadatas", [])
    embeddings_list = results.get("embeddings", [])

    if not documents:
        return []

    # Step 3: Get embeddings for all candidates
    # If ChromaDB didn't return embeddings, re-embed the documents
    if not embeddings_list:
        from ai.embeddings import embed_batch
        candidate_embeddings = embed_batch(documents)
    else:
        candidate_embeddings = np.array(embeddings_list)

    # Step 4: MMR selection
    query_vec = query_embedding.reshape(1, -1)
    
    # Compute similarity of all candidates to query
    # Cosine similarity = dot product of normalized vectors
    norms = np.linalg.norm(candidate_embeddings, axis=1, keepdims=True)
    norms[norms == 0] = 1  # Avoid division by zero
    normalized_candidates = candidate_embeddings / norms
    
    query_norm = np.linalg.norm(query_vec)
    if query_norm > 0:
        normalized_query = query_vec / query_norm
    else:
        normalized_query = query_vec

    query_similarities = (normalized_candidates @ normalized_query.T).flatten()

    # Iteratively select using MMR
    selected_indices = []
    remaining_indices = list(range(len(documents)))

    for _ in range(min(top_k, len(documents))):
        if not remaining_indices:
            break

        if not selected_indices:
            # First selection: pick the most relevant
            best_idx = remaining_indices[
                np.argmax([query_similarities[i] for i in remaining_indices])
            ]
        else:
            # Subsequent selections: balance relevance and diversity
            best_score = -float('inf')
            best_idx = remaining_indices[0]

            for idx in remaining_indices:
                # Relevance to query
                relevance = query_similarities[idx]

                # Maximum similarity to any already-selected chunk
                max_sim_to_selected = max(
                    float(np.dot(normalized_candidates[idx], normalized_candidates[s]))
                    for s in selected_indices
                )

                # MMR score
                mmr_score = lambda_mult * relevance - (1 - lambda_mult) * max_sim_to_selected

                if mmr_score > best_score:
                    best_score = mmr_score
                    best_idx = idx

        selected_indices.append(best_idx)
        remaining_indices.remove(best_idx)

    # Step 5: Build results
    retrieval_results = []
    for idx in selected_indices:
        score = max(0.0, min(1.0, 1.0 - (distances[idx] / 2.0)))
        meta = metadatas[idx] if metadatas else {}
        chunk_index = meta.get("chunk_index", idx) if meta else idx

        retrieval_results.append(RetrievalResult(
            text=documents[idx],
            score=score,
            metadata=meta,
            chunk_index=int(chunk_index),
        ))

    return retrieval_results

1. What is a Text Embedding?

A text embedding is a function f: String → ℝⁿ that maps variable-length text to a fixed-dimensional vector such that semantically similar texts produce vectors with high cosine similarity.

f("The cat sat on the mat")   → [0.023, -0.145, 0.892, ..., 0.341]  (384 dimensions)
f("A feline rested on a rug") → [0.019, -0.138, 0.887, ..., 0.339]  (384 dimensions)

cosine_similarity(f(text1), f(text2)) ≈ 0.94  (high — semantically similar)

The key property: semantic similarity in text space maps to geometric proximity in vector space.

Texts about the same topic cluster together. Unrelated texts are far apart. This is what enables similarity search — find the nearest vectors to a query.

2. Learning Embeddings in Transformer Architectures

All three models are based on the Transformer encoder (BERT family).

Tokenization

Input:  "The cat sat on the mat"
Tokens: ["[CLS]", "the", "cat", "sat", "on", "the", "mat", "[SEP]"]
IDs:    [101, 1996, 4937, 2938, 2006, 1996, 13523, 102]

Self-Attention (simplified)

Q_i = W_Q · E_i    (query)
K_j = W_K · E_j    (key)
V_j = W_V · E_j    (value)

attention_weights = softmax(Q_i · K_j^T / √d_k)
output_i = Σ_j (attention_weights_j · V_j)

Pooling: Token Vectors → Sentence Vector

Self-Supervised Pre-Training: Masked Language Modeling

Before fine-tuning for embeddings, the base model learns language by predicting masked tokens. No labels needed — the text itself provides the training signal.

Key insight: By learning to predict masked words from context, the model develops deep understanding of language — word meanings, grammar, and relationships — all without any labeled data.

Fine-Tuning: Contrastive Learning on Sentence Pairs

After pre-training, the model is fine-tuned to produce good sentence embeddings using labeled pairs.

Result: After fine-tuning on ~1B sentence pairs, the model produces embeddings where paraphrases are close and unrelated texts are far apart — exactly what RAG retrieval needs.

Training: Contrastive Learning

Models are fine-tuned with Multiple Negatives Ranking Loss:

For each anchor a_i in batch:
    positive = p_i (its pair)
    negatives = all other p_j in batch

    loss = -log(exp(sim(a_i, p_i)/τ) / Σ_j exp(sim(a_i, p_j)/τ))

Each batch of N pairs gives N positives and N×(N-1) negatives — efficient without explicit negative mining.

Cosine Similarity

cos_sim(a, b) = (a · b) / (||a|| × ||b||)

Range: [-1, 1]
  1  = identical direction (same meaning)
  0  = orthogonal (unrelated)
 -1  = opposite direction

Why cosine over Euclidean? Embeddings are L2-normalized. Cosine is invariant to magnitude — only direction matters. Two texts about the same topic point the same direction regardless of length.

In ChromaDB: score = 1.0 - (distance / 2.0)

🗄️ Vector Store & Retrieval: HNSW Algorithm

ChromaDB uses HNSW (Hierarchical Navigable Small World) graphs for approximate nearest neighbor search. This page explains how it works.

The Problem: Finding Similar Vectors

Given a query vector, find the K most similar vectors among N stored vectors. Brute-force compares against all N — too slow for millions of vectors.

Collection SizeBrute Force O(n×d)HNSW O(log n)
1,000 vectors~1ms~0.1ms
100,000 vectors~100ms~1ms
10,000,000 vectors~10s~5ms

HNSW: Multi-Layer Graph Structure

HNSW builds a hierarchy of graphs. Higher layers have fewer nodes with long-range connections (for fast coarse navigation). Lower layers are denser (for precise local search).

Why O(log n)?

Each layer halves the number of nodes (probabilistically). With N vectors:

  • Number of layers ≈ log(N) — similar to a skip list
  • Steps per layer ≈ constant (bounded by M, the max connections)
  • Total steps ≈ O(log N) — much faster than scanning all N
N = 1,000,000 vectors
log₂(1,000,000) ≈ 20 layers
Steps per layer ≈ M = 16 neighbor comparisons
Total comparisons ≈ 20 × 16 = 320   (vs. 1,000,000 for brute force)

Trade-off: Speed vs. Recall

HNSW is approximate — it may miss the true nearest neighbor if the graph doesn't have a direct path. The ef parameter controls this:

ef (beam width)RecallSpeedUse case
10~85%Very fastReal-time search, tolerates misses
50~95%FastDefault (good balance)
200~99%SlowerHigh-precision retrieval
N (all)100%Brute forceExact search (defeats purpose)

For this course (<10K vectors), the recall difference is negligible. HNSW matters at scale.

🏗️ RAG System Architecture

How the components fit together — and where each piece runs.

The RAG Pipeline

Document → Chunk → Embed → Store → [Query] → Retrieve → Augment Prompt → Generate Answer

Why RAG?

LLMs have two types of knowledge:

  • Parametric knowledge — baked into weights during training (static, may be outdated)
  • Source knowledge — provided in the prompt at query time (dynamic, always current)

RAG provides source knowledge by retrieving relevant document chunks and injecting them into the prompt.

Key Parameters

Parameter What it controls Trade-off
chunk_size Characters per chunk Small = precise but fragmented; Large = contextual but noisy
chunk_overlap Shared characters between consecutive chunks More overlap = less information loss at boundaries
top_k Number of chunks retrieved More = broader context; fewer = more focused
embedding_model Which model converts text to vectors Larger = better quality but slower
temperature LLM creativity in generation Lower = more faithful to context; higher = more creative

Why Not LangChain?

You may have seen tutorials using LangChain to build RAG pipelines in a few lines. LangChain wraps LLM calls, embeddings, vector stores, and retrieval chains behind high-level abstractions.

In this course, we intentionally do not use LangChain. Every step is implemented explicitly:

  • Chunking → ai/chunker.py (plain Python sliding window)
  • Embeddings → ai/embeddings.py (direct sentence-transformers calls)
  • Vector store → ai/vectorstore.py (direct ChromaDB client)
  • LLM calls → shared/llm_client.py (direct Ollama HTTP API)
  • Prompt construction → ai/generator.py (string formatting)

Why? So you see exactly what happens at each stage. When LangChain does RetrievalQA.from_chain_type(...), it hides the embed → search → format → generate flow. By writing it yourself, you understand the trade-offs and can debug each piece independently. Once you understand the fundamentals, adopting any framework becomes straightforward.
